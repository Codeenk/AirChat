# AirChat — Sealed Sender (metadata confidentiality)

Status: **relay implemented; client wiring in progress.** This document
describes the design; the code is the authority and this file must be updated
whenever the wire format changes.

Landed so far:

* relay — tag registry, sealed send/deliver/ack/receipt, uid-free wake,
  mixing batch, self-subscribed groups, 24h sweep (`ConnectionRelay.ts`,
  `src/db/delivery_tags.ts`, migration `0003_sealed_sender.sql`);
* client — `RatchetBundle.deliveryTag` (optional, so older bundles still
  decode) and the delivery tag field on the wire.

Not yet landed: the client send/receive/background wiring and the tag lifecycle
(`delivery_tag.dart`), the client-side jitter and cover traffic, and tests for
the sealed path. Until those land, sealed delivery is **not** in use by any
client — every conversation still runs the legacy named transport, and leaks
#1–#8 in the table below therefore still apply on the wire.

Related: `SECURITY.md` (storage rules), `SECURITY_THREAT_MODEL.md` (adversary),
`SECURITY_DESIGN.md` (crypto per chat), `SECURITY_GROUP_CRYPTO.md` (MLS).

## 1. The problem

Every earlier version of AirChat protected **content** but leaked **metadata**.
Message bodies were end-to-end encrypted, yet the relay knew — explicitly,
persistently, and in its logs — who talks to whom:

| # | Leak | Where |
|---|------|-------|
| 1 | `send_packet{recipientUid}` sent from a socket *already authenticated as the sender's uid* | live wire |
| 2 | `EphemeralPacket{id, senderUid, recipientUid, payload}` stored at key `msg:<recipientUid>:<packetId>` | Durable Object storage, 24h |
| 3 | `ack{packetId, senderUid}` — the recipient names the sender back to the relay | wire + delete |
| 4 | `read_receipt{packetId, senderUid}` | wire |
| 5 | `delivery_failed{…, recipientUid}` handed to the sender | wire + push |
| 6 | Push data `{type:'wake', senderUid}` | **Google/FCM** |
| 7 | Push data `{type:'group_wake', senderUid, groupId}` | **Google/FCM** |
| 8 | Group packets persisted with `senderUid` under `grp:<groupId>:<packetId>` | DO storage |
| 9 | `POST /api/group/register` — one client posts the **entire memberUid roster** | D1 |
| 10 | `console.log("[relay] enqueue … for <recipient> (sender <uid>)")` | logs |

For a hostile relay, cloud provider, or a network observer, #1/#2/#9 are the
whole social graph — the thing end-to-end encryption is supposed to make
unnecessary to trust. Leaks #6/#7 additionally hand the graph to a third party.

## 2. Goal and non-goal

**Goal.** The relay must be able to deliver a message without learning *who
sent it*. Concretely: no `uid` of a sender appears anywhere in the relay's
transient state, persisted state, logs, or outbound push payloads, and the
relay holds no `uid ↔ uid` edge.

**Non-goal (stated honestly).** This alone does not defeat a relay that is
*actively* correlating a live connection's IP address and timing with another
live connection. See §7. Absolute unlinkability against a global, live,
adversarial relay requires an anonymity layer (independent relays, cover
traffic, delays) — §7 records the residual precisely rather than implying more
than is true.

## 3. The core move: address a device, not a user

Everything rests on one substitution.

* **Before:** a device is addressed by its **uid** — a stable, public, human-
  meaningful identifier that the relay also uses for identity registration.
* **After:** a device is addressed by a **delivery tag** — 32 random bytes
  (base64url, 256 bits) generated on-device, meaningless, and rotated.

`uid` continues to exist for the identity directory (so peers can find each
other's keys) and for the *legacy* transport. It is simply **not used to route
sealed traffic**.

```
delivery tag   dt  = 32 random bytes, generated on-device
reply tag      rt  = the sender's own dt, quoted so the reply has a return path
packet id      pid = 16 random bytes, generated by the sender
sender hint    hint = 16 bytes, HKDF(session secret)   -- see §5.4
```

Neither tag is derived from a uid, a username, or a key, so a tag cannot be
reversed or brute-forced into an identity.

## 4. Wire format

### 4.1 Registration (replaces implicit uid addressing)

The client opens the tunnel and registers its tag:

```jsonc
{ "action": "seal_register", "tag": "<dt>", "fcm": "<device token>" }
```

The relay binds this socket to `tag` and records only `(tag, fcmToken)` with a
TTL. **No uid is written down.** The socket may *additionally* perform the
legacy `auth` handshake to keep old-style traffic working during migration, but
that authentication is never associated with the tag in storage.

Registration is unauthenticated by design: a tag confers no privilege. It only
means "deliver to me what is addressed to this tag". The tag is 256 bits of
device-local randomness, so it is not guessable; if a tag is somehow claimed by
someone else, the newest registration wins and the legitimate device reclaims it
on its next connect (every connect re-registers).

### 4.2 Sending (sealed)

```jsonc
{
  "action": "seal",
  "to":   "<recipient dt>",
  "reply":"<sender's own dt>",     // return path for status, NOT an identity
  "packetId": "<pid>",
  "body": "<base64 opaque envelope>",
  "hint": "<base64 sender hint>"   // optional, §5.4
}
```

The relay:

1. checks `to` is a known, unexpired tag (if not: generic `404`, so tags cannot
   be enumerated or validated);
2. stores `msg:<to>:<pid>` → `{ pid, body, reply, hint, ts }`;
3. delivers to the live socket bound to `to`, or wakes it.

**The stored record contains no uid.** The storage key contains the recipient's
tag — which the relay must know in order to deliver at all — but a tag is not an
identity.

### 4.3 Delivery to the recipient

```jsonc
{ "type": "sealed_message", "packetId": "<pid>", "body": "…", "hint": "…", "timestamp": 0 }
```

There is deliberately **no `senderUid`**. The recipient learns who sent the
message by *decrypting it*: a Double Ratchet or MLS envelope authenticates its
sender cryptographically. The relay is not asked, and is not trusted, to say who
the sender was.

### 4.4 Acknowledgement and receipts (no edge assertion)

```jsonc
{ "action": "seal_ack",     "tag": "<my dt>", "packetId": "<pid>", "reply": "<sender rt>" }
{ "action": "seal_receipt", "tag": "<my dt>", "packetId": "<pid>", "reply": "<sender rt>" }
```

The recipient deletes `msg:<my tag>:<pid>` and the relay forwards
`{type:"seal_status", packetId, status}` to the connection bound to `reply`.

Two properties matter:

* the recipient never states *who* the sender was — only which opaque packet it
  consumed;
* deletion is scoped to `tag`, and the relay only honours an ack for a tag from
  the socket that registered it. So an ack grants no power over anyone else's
  mail and needs no identity to authorise.

### 4.5 Push without identity

```jsonc
{ "type": "sealed_wake" }        // nothing else — no sender, no group, no uid
```

A wake only needs to say "you have mail". The device wakes, reconnects, flushes
its own queue and decrypts; attribution happens on-device from the envelope.
Google therefore learns *that* a device has mail, never *who* it is from.

## 5. Attribution and replies on the client

### 5.1 Sender attribution

The transport no longer names the sender, so the client derives it:

* **MLS groups** — resolved from the MLS ratchet tree / credential, as the
  ciphertext already binds the sender's leaf. No hint needed.
* **1:1 Double Ratchet** — resolved via the `hint` (§5.4).
* **Legacy X25519** — carries no sender identity inside the payload, so it
  **cannot** ride sealed delivery; it keeps the legacy transport (§6).

### 5.2 Why the reply path is a tag, not a uid

A receipt must travel back to the sender. Using the sender's uid would
reintroduce leak #5; using a per-peer pseudonym would let the relay build a
stable pseudonymous edge. Using the sender's own **device tag** means the relay
learns, at most, "tag R and tag B are in contact" — a graph of random numbers
with no identity attached.

### 5.3 Rotating tags

Tags rotate on a timer and on every app start, so a long-lived tag cannot be
used as a stable device identifier across sessions. A rotated tag is published
to contacts via the directory and to the relay at registration; the old tag is
dropped with its TTL.

### 5.4 Sender hints

`hint = HKDF-SHA256(ikm = session secret, info = "airchat-sender-hint", len = 16)`.

Both peers can compute it once a session exists; the recipient keeps a
`hint → peer` cache so attribution is O(1) instead of trial-decrypting against
every stored session. To anyone else — including the relay — it is 16 opaque
bytes, and it changes when the session's keys change.

The hint is an *optimisation, not an authority*: if it is missing or unknown, the
client falls back to trying its active sessions, and the payload's own
authentication is what actually decides who the sender is.

## 6. Migration and backwards compatibility

Sealed routing is negotiated, never assumed, so a v1.8.0 client keeps working
against the new relay and vice versa:

| Sender | Recipient | Path used |
|--------|-----------|-----------|
| sealed | sealed | fully sealed — no uid in transit or at rest |
| sealed | legacy | relay resolves the tag and attaches `senderUid` so the old client can attribute |
| legacy | any | legacy `send_packet` / `send_group_packet`, sender still named |

Sealing only becomes real once **both** ends are new, which is exactly when the
payload can self-attribute. A peer that has published no tag is simply messaged
the legacy way. This makes rollout gradual and self-healing: no flag day, no
version lock, and a mixed population degrades to the old behaviour rather than
breaking.

## 7. Residual gaps (read this before claiming "unlinkable")

1. **Live correlation.** A relay that terminates both peers' connections can
   correlate by IP address and timing even when every packet is opaque. Sealed
   routing removes the relay's *stored, logged, and third-party-visible* graph;
   it does not stop a live adversary from inferring one. Mitigations
   (independent relays, cover traffic, forced delays) are tracked separately;
   §8 describes the timing defences that *are* in place.
2. **Traffic analysis at the edges.** The *timing* and *size* of a send remain
   observable at the moment of submission.
3. **Semi-trusted relay for availability.** A malicious relay can drop, delay,
   or re-order sealed traffic. It cannot read it, and it cannot learn identities
   from it, but it can deny service. Tags are unauthenticated for receive, so a
   relay that leaks a tag could in principle allow a claim on it; the newest
   registration wins and the owner reclaims on next connect.
4. **No anonymity network.** This is not a mixnet. It is the strongest property
   achievable with a single relay and no added latency budget.
5. **Single device per user** (`deviceId = 1`), as before; no multi-device.

## 8. Timing defences

Chosen deliberately over "do nothing" because send timing is a first-class
signal; chosen as jitter-and-batching rather than a full mixnet because a
messenger cannot absorb multi-second delays by default.

* **Client-side jitter** — each outbound sealed packet is delayed by a random
  interval before submission, so submission time is not send time.
* **Client-side batching** — packets composed within the same short window are
  submitted together, so a burst of conversation collapses into fewer,
  less-informative submissions.
* **Relay-side mixing batch** — sealed packets are held briefly, **shuffled**,
  and delivered on a timer rather than immediately. Arrival order and arrival
  time therefore do not map to delivery order or delivery time, which is what
  makes the relay's own real-time view far less useful for correlation.
* **Optional cover traffic** — an opt-in setting emits dummy sealed packets at
  a random rate. Recipients drop them on decrypt failure; an observer cannot
  distinguish them from real traffic. Costs battery and data, so it is off by
  default and documented as such.

None of these make correlation impossible for a global observer; they raise its
cost and its false-positive rate. That is the honest claim.

## 9. Storage rules

Consistent with `SECURITY.md` ("all stored data must have TTLs — no permanent
server-side records"):

| Store | Contents | TTL |
|-------|----------|-----|
| DO `msg:<tag>:<pid>` | `{pid, body, reply, hint, ts}` | 24h (unchanged) |
| DO `grp:<groupTag>:<pid>` | `{pid, body, ts}` | 24h |
| D1 `device_tags` | `(tag, fcm_token, expires_at)` — **no uid column** | 30d, refreshed on register |
| D1 `group_subscriptions` | `(group_tag, member_tag, expires_at)` — **no uid column** | 30d, refreshed on send |

The absence of a `uid` column in the two new tables is the point: there is no
row anywhere that joins a tag to a person.

## 10. Group metadata

`POST /api/group/register` used to accept a whole roster, which meant the relay
held a complete "who is in which group" graph (leak #9). Group membership is now
**self-subscribed**: each member registers *its own* `(group_tag, member_tag)`
pair for the groups it belongs to. The relay never receives a roster from a
third party and never learns uids. Wake fan-out reads the subscription table and
addresses member tags.

Consequence to be honest about: a member that has never connected cannot be
woken for a group, because the relay has no row for it. This matches the
existing behaviour in practice (a member must join before it can be messaged),
but it is a real difference from creator-registers-everyone.

### Open design question: sender attribution for 1:1

§5.4 proposes `hint = HKDF(session secret)`, but **libsignal does not expose the
session's root key**, so that value cannot currently be derived. The obvious
substitute — a hint computed from the two identity keys — is *worse than
nothing*: identity keys are public in the directory, so the relay could compute
the hint for every candidate pair and match it, rebuilding the graph it is
supposed to lose. Until a non-linkable hint exists, the plan is for the
recipient to attribute by trying its established sessions (the payload's own
authentication is what decides, per §5.4), with the `hint` field left reserved
and unpopulated.
